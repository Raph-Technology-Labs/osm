# Station 2 camera behind a 100 Mbit switch

- **Date seen:** 2026-09-24
- **Area:** Network / camera (`cam2`, 192.168.7.41, host NIC `enp4s0`)
- **Severity:** High: station 2 could not start a session
- **Status:** Fixed (switch replaced with a 1 Gbit switch). Driver hardened.
- **Fix commit(s):** `5a7444b` (driver). The hardware change isn't in git.

## Summary
The station 2 camera and the PC's `enp4s0` port were connected through a
10/100 switch, so the link ran at 100 Mbit/s. Station 2 at 30 fps needs about
500 Mbit/s, so session start failed as soon as the configured bandwidth cap
(600 Mbit/s) was applied.

## Symptom
```
app.camera.camera_driver.CameraConnectionError: cam2: Lucid connect failed:
throughput_limit_mbps=600 is outside this camera's range 25-100 Mbit/s
POST /api/v1/inspection/session/start HTTP/1.1" 400 Bad Request
```

Earlier signs:
- `ethtool enp4s0` showed `Speed: 100Mb/s`.
- `focus_live.py` on this camera got about 4.5 fps at full resolution.

## Diagnosis
- The maximum of the camera's `DeviceLinkThroughputLimit` equals its current
  Ethernet link speed. A maximum of 100 Mbit/s means the **camera** side was
  also at 100 Mbit/s, not only the PC side.
- Both ends on the same switch running at 100 Mbit/s points to the switch
  (a 10/100 model, common on PLC networks) rather than one bad cable.
- After the switch swap, `/sys/class/net/enp4s0/speed` read `1000`.

## Root cause
The 192.168.7.x network was built for the PLC, which needs very little
bandwidth, and uses a 10/100 switch. When the camera was added to that network,
nobody checked the link speed. A full-resolution GigE camera needs a 1 Gbit
path end to end.

Bandwidth needed: 1920 x 1080 x 1 byte (Mono8) x 30 fps ≈ 62 MB/s ≈ 500 Mbit/s.

## Actions taken
- **Hardware:** replaced the switch with a 1 Gbit switch. `enp4s0` now links
  at 1000 Mbit/s.
- **Driver (`LucidCamera._configure_throughput`):**
  - A cap above the link speed is now lowered to the link speed with a warning,
    since the link can't carry more anyway.
  - An fps that doesn't fit now fails with a message naming the link speed, for
    example `fps=30 doesn't fit through 100 Mbit/s (max 5.4 fps ...; camera
    link is 100 Mbit/s) -- ... get the camera onto a faster link`.
- **Config:** `cam2.throughput_limit_mbps: 600`, which caps the camera below
  the 1 Gbit link and protects the shared PLC network.

## Prevention
- Tests: `test_throughput_limit_above_link_speed_is_capped_at_link_speed` and
  `test_fps_too_high_for_slow_link_names_the_link_speed` (in
  `tests/test_lucid_strobe.py`).
- **Commissioning checklist item:** for every camera NIC, check
  `cat /sys/class/net/<nic>/speed` is `1000` (or more) before the first
  session, and use only gigabit switches on any network that carries a camera.

## Follow-ups
- Confirm the camera's own link reports 1000 as well. On the next session
  start, the log line `throughput limit 600 Mbit/s (max N fps)` should show
  N ≥ 30.
- The PLC and controller share this switch with the camera. Watch for Modbus
  latency while station 2 streams; the 600 Mbit/s cap is the main protection.
